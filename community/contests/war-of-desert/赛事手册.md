## 1. 赛事定义

Desert Arena 是 1v1 无头算法对抗赛：红蓝双方在程序生成的沙漠地形上争夺 VP、保护母舰，选手提交独立 Bot 程序，官方裁判按固定规则裁决。

正式赛有三个不变式：

1. **规则可复现**：同一 `seed + 生成器 + tickLimit + orderLog` 必得同一局。引擎不读墙钟、不取系统随机数。
2. **选手进程隔离**：Bot 是独立操作系统进程，只通过 stdin/stdout 的单行 JSON 通信。超时 kill、崩溃重启、非法结构判罚都由裁判执行，不依赖 Bot 自律。
3. **两条独立信号**：单局胜负（五级判定链）决定对抗结果；七领域加权总分衡量“赢得好不好”。正式名次按胜负拟合 Bradley–Terry，加权总分单独成榜，两者不互相覆盖。

## 2. 赛季结构

正式赛按以下阶段推进，次序不可交换：

| # | 阶段 | 产出 | 责任方 |
|---:|---|---|---|
| 1 | 报名与资格审查 | 选手名册、参赛声明 | 主办方 |
| 2 | 发放选手包 | `workspace/`（规则、模板、参考 Bot、计时器、**arena/ 引擎与裁判源码**） | 主办方 |
| 3 | 编码期 | `workspace/submission/<选手名>_bot.go` | 选手 |
| 4 | 强制收卷 | `submissions/<选手名>_bot.go` + SHA-256 + 用时 + `accepted` | 主办方 |
| 5 | 编译与封存 | `bots/bin/*.exe`、`bots/seal-records/<赛季>.json` | 主办方 |
| 6 | 赛程冻结 | `../algorithm-contest/tests/history-seasons/formal-v12/赛程.json` | 主办方 |
| 7 | 正式对局 | `结果.jsonl`、`replays/match-*.json` | 裁判 |
| 8 | 评分与公示 | `成绩.md`、`成绩_加权总分.md`、`成绩.json` | 主办方 |
| 9 | 申诉与仲裁 | 仲裁记录 | 裁判长 |
| 10 | 颁奖与归档 | 赛季归档、榜单更新 | 主办方 |

**时间线（默认）**：编码期目标 90 分钟，最迟 120 分钟强制收卷。解压选手包即开始计时，暂停必须写入赛务记录。正式对局不设选手在场要求，收卷后由主办方统一编译、冻结赛程、批量跑完。

## 3. 参赛与交付

### 3.1 提交物

只有一个文件：`workspace/submission/<参赛选手名称>_bot.go`，`package main`，编译后是独立可执行程序。
文件名＝选手目录名中 `@` 之后的部分 + `_bot.go`（如 `rts-contest@HY-4` → `HY-4_bot.go`）。

选手可以：

- 只用标准库，自己实现 stdin/stdout 协议；
- 使用选手包自带的 `arena/workspace/botkit`（协议读写、地图解码、一步寻路）。

**不允许** import 自己新增的包或任何第三方库：收卷只冻结 `<选手名>_bot.go` 单文件，其他源码不会随卷带走，会导致收卷后编译失败。

### 3.2 禁止项

- 读写文件、访问网络、启动子进程、调用系统时间影响决策（读取时间不禁止，但不得据此改变动作序列）；
- 读取 `workspace/` 之外的路径，或读取其他选手的目录；
- 修改裁判、引擎、赛程、结果、封存记录；
- 硬编码单张地图的坐标：正式赛逐场换 seed，且同场换边两局；
- 跨局保存状态：每局都会重启进程并重发 hello。

**执行侧强制手段（v1.3 起）**：上面几条不再只是纸面规则。裁判用 Windows Job Object 给每个选手进程加硬约束——

| 约束 | 手段 | 违反后果 |
|---|---|---|
| 不得派生外部进程 | `ActiveProcessLimit=1` | 派生调用直接失败 |
| 内存不得失控 | 单进程 512 MiB / 整个 Job 1 GiB | 分配失败或进程被杀 |
| 不得污染工作区 | 每局在一次性临时目录内运行，结束后删除 | 相对路径写不到仓库 |
| 最小环境变量 | 只透传 `SystemRoot/TEMP/TMP/PATH` 等运行时必需项 | 拿不到令牌与代理配置 |

**仍未覆盖**：文件系统读权限与出网。这两条需要独立低权账户或容器；当前执行链在 Windows 上靠 Job Object + 临时工作目录 + 封存哈希校验兜底。组织方若要在高奖金场景使用，应把选手进程放进独立的低权账户或容器，并在赛务记录里注明。

### 3.3 编译与封存

```bash
cd war_of_desert
go run ./cmd/arena build          # 编译全部 entries，写 bots/seal-records/<赛季>.json
```

封存记录包含：

- 每个选手源码目录下所有 `.go` 文件的 SHA-256；
- 共用库 `workspace/botkit`、`workspace/refbot` 的 SHA-256；
- 编译产物路径。

**一季一本**：文件名取自配置名（`formal_v19`、`experiment_v19_700`），
`build` 只覆盖本赛季节的那一本。两个赛季并存时各自校验各自的封存，
不会因为给实验赛季编译过一次，就改动正式赛季的封存记录。

编译失败会中止 `build` 并报错：组织方必须先剔除该选手（或让其修复）再重跑，不能带着半份赛程开赛。缺 `<选手名>_bot.go`、收卷哈希与源码哈希不一致，按“未提交”处理，由组织方在赛程中移除该选手并记录原因。

### 3.4 选手包自检

```bash
cd war_of_desert
go run ./cmd/arena check -seed 20261109
```

自检跑一场换边两局，打印每局胜者、判定层级、VP、七领域总分、故障数和确定性复核结果。`CHECK_OK` 只代表流程跑通，不代表强度。

选手侧的等效入口在选手包里：双击 `本地对局.bat`（= `arena/` 下的
`go run ./cmd/arena local -bot ..\bot.exe -seeds 2`）。包里那份 `arena/` 就是本仓库
`war_of_desert/` 的源码副本，由 `赛务.py --sync-engine` 同步、发卷时自动刷新，
所以选手本地看到的行为与赛场一致。`arena/` 不入库（从引擎同步即可重建）。

## 4. 规则基线

完整数值以 Go 原生引擎 `internal/sim`（v1.9.2）为准；`engine/oracle/` 只用于第 1 季（v1.0）历史复现，不参与当前赛季裁决。这里只列选手必须知道的：

| 项 | 值 |
|---|---|
| 地图 | 256×256 格，1 格 = 6 px（物理 10 m），像素世界 1536×1536，物理 2.56 km；默认 `minecraft` 生成器 |
| 逻辑节奏 | 20 tick/s，单局 1500 tick（75 秒逻辑时间） |
| 决策预算 | 每次 `decide` 120 ms；开局 `init` 2000 ms |
| 指令延迟 | 固定 1 tick：本拍提交，下一拍生效 |
| 初始配置 | 双方 500 CU、0 RU；母舰 + 2 LAV |
| 资源 | CU/RU 双资源运输线：采集车（SALVAGER）在资源点装载→回程→卸货；资源点**按镜像成对**分配类型，每对同类（两侧 RU 数量必然相等）；母舰 RU 基础收入 0.20/tick |
| 母舰 | 四子系统分配 armour/repair/attack/range，和必须 100，实际值按 5%/tick 向目标过渡；自愈仅在**脱战 60 拍后**生效（持续挨打不回血）。v1.9.1 沿用 v1.4 数值：HP 1800 / 攻击 13 / 移速 0.30 / 坡限 4 高程单位（射程、射速、视野、装甲、弹道、四子系统一律不变） |
| 生产 | 生产线 = 1 + 工业科技（封顶 3）；队列**跳过式出队**（v1.2）：从队首找第一个 CU/RU 付得起的单位出队，付不起的项原地保留 |
| 科技 | 火力、装甲两条线性树；机动、工业两条交叉树 |
| 弹道 | 二次阻力 + 重力，RK4 积分；伤害由落速、弹种、装甲与克制决定 |
| 视野 | 本赛季 `vision=false`：全图可见，无战争迷雾 |
| 胜负链 | 母舰被毁 → VP → KD 差 → 母舰 HP 比例 → 平局 |
| 七领域权重 | VP 控制 30%、歼敌 20%、保存兵力 15%、母舰完整度 15%、KD 差 10%、战场控制 5%、推进效率 5% |

**故障出局**：连续 3 次故障判负（`maxStrikes=3`，`strikeMode=consecutive`）。双方同拍达到上限判平局。

## 5. 协议契约

### 5.1 消息流

```text
裁判 → Bot   {"type":"hello", ...}          开局一次，含地图、规则常量、时序
Bot  → 裁判  {"ready":true}                  初始化完成
裁判 → Bot   {"type":"tick", ...}            每 tick 一次
Bot  → 裁判  {"actions":[...]}               每 tick 一次
裁判 → Bot   {"type":"end","result":{...}}   终局一次
```

`ready` 是正式版新增的握手确认：它把 `init` 与第一次决策的计时分开，避免开局读图被算进 120 ms 预算。

### 5.2 线体积与编码

- 所有消息为 UTF-8、单行 JSON，不得包含未转义换行。
- 所有消息单行上限 **128 KiB**（v1.2 契约，`internal/protocol.MaxLine`）。
- `hello`：**当前约 110 KB**，来自地图 RLE+base64 编码，在 128 KiB 契约内；512² 前仍需压缩/分块。
- 地图层格式 `rle+b64/1`：`base` / `surf` 为 `(值, 次数-1)` 字节对流 + base64，`elev` 为原始 1 字节/格 + base64。解码实现见 `internal/protocol.DecodeMapLayers` 与 `workspace/botkit`。

### 5.3 计时窗口

每次决策的计时从裁判写出 `tick` 行开始，到读完整 `actions` 行结束。超时、坏 JSON、结构非法、进程崩溃或被杀，各记 1 次故障。

思考耗时超过 1 个 tick（50 ms）但未超 120 ms，只记 `late`，不改判定——指令本来就固定晚 1 tick 落地。

### 5.4 故障语义

| 情况 | 处理 |
|---|---|
| 超时（>120 ms 未交完整行） | kill 进程，记故障，本拍无动作；重启后继续 |
| 进程崩溃/退出 | 记故障，本拍无动作；重启后继续 |
| 返回不是合法 JSON / 不是 `{actions:[...]}` | 记故障，本拍作废；进程保留 |
| 动作结构性非法（id 不属于自己、坐标越界、重复单位动作、动作过多） | 记故障 |
| 动作语义非法（撞山、目标已死、槽位满、钱不够） | 只丢弃该条动作并记入 `rejected`，**不判故障** |

重启语义：kill 后重新拉起同一可执行文件，重发 hello、等待 ready；故障计数不清零，直到连续 3 次红牌。

## 6. 赛程

### 6.1 生成规则

```bash
go run ./cmd/arena plan
```

- 选手两两组合，每个基准 seed 跑一遍完整循环；
- 每场对阵默认换边两局：同一 seed、同一张点对称地图，红蓝互换，双方各自重启进程；
- 场次 seed = 基准 seed + 已排场次数，保证 `plan` 可重放出逐字节相同的 `赛程.json`；
- 场次数 = `N×(N-1)/2 × len(seeds)`，局数 = 场次数 × 2。

第 1 季基准赛：5 名选手、2 个基准 seed → **20 场 / 40 局**，实际 seed 从 `20261109` 递增到 `20261129`。

### 6.2 冻结与变更

`run` 只读 `赛程.json`，不读赛季配置的赛程段。赛程一旦冻结：

- 不得因某方要求单独改 seed 或对手；
- 因引擎缺陷导致整场作废时，必须整场重跑并保留原结果文件为 `.void`；
- 新增选手只能进入下一轮循环，不得插入已开始的赛程。

## 7. 计分与排名

### 7.1 单局

- 胜负：五级判定链，输出 `winner / level / reason`；
- 质量：七领域计分卡，每项 0–100，按权重加总为 `total`；
- 故障：超时、崩溃、结构非法逐条记录；红牌判负记 `level=0`；
- v1.2 起计分**完全确定性**：已移除按墙钟折算的「算力表现」域，决策耗时只作诊断记录。同一 `orderLog` 重跑，单位状态、事件、胜负与七个领域、总分完全一致。

### 7.2 正式名次（Bradley–Terry）

- 每局作为一条数据：胜 1、平 0.5、负 0；
- MM 迭代拟合，基准锚 = 名册第一名选手，锚定 0；
- 每对选手加一局虚拟平局，抑制全胜/全败导致的最大似然发散；
- 95% 区间按“对局整块”重抽样 200 次；
- 刻度：差 400 分 ≈ 10:1 胜率。

区间宽度取决于局数。40 局、5 名选手时区间通常有 200–400 分宽，**排名接近的选手不能仅凭点估计断言强弱**。第 1 季 `Bulwark`（-59.4）与 `Starter`（-74.6）的区间几乎完全重叠，谁更强在统计上无法区分。

### 7.3 加权总分榜

七领域总分按选手合计与场均分单独排名。它与 BT 名次可能不一致，这是设计目标而非错误：一套稳健但保守的打法可能总分很高、胜负一般；一套搏杀打法可能赢得多、掉分也多。第 1 季就出现了 `Starter` 总分第三（884.1）但 BT 垫底（-74.6）的分歧。

## 8. 赛务计时与强制收卷

选手侧：

```bash
cd workspace
python -X utf8 clock.py
```

**多选手目录（algorithm-contest/）**：每个选手目录用仓库根目录的 `赛务.py` 单独计时，
或直接在裁判台的「编码」页签里点「发卷」/「开始编码」——目录为空时会先铺选手包再开始计时。

```bash
python -X utf8 赛务.py --dir "algorithm-contest/rts-contest@x" --start
python -X utf8 赛务.py --dir "algorithm-contest/rts-contest@x" --status
python -X utf8 赛务.py --dir "algorithm-contest/rts-contest@x" --pause --note="模型限额"
python -X utf8 赛务.py --dir "algorithm-contest/rts-contest@x" --freeze
```

赛务记录写在 `<选手目录>/.赛务.json`，收卷产物在 `<选手目录>/submissions/`
（`<选手名>_bot.go` + `交卷记录.json`：SHA-256、字节数、用时、accepted）。

组织侧：

```bash
cd war_of_desert
python -X utf8 开赛.py                 # 开赛/重置
python -X utf8 开赛.py --status
python -X utf8 开赛.py --pause --note="原因"
python -X utf8 开赛.py --resume
python -X utf8 开赛.py --freeze-due    # 到 120 分钟强制收卷
python -X utf8 开赛.py --freeze        # 立即收卷
```

- 默认目标 90 分钟、强制收卷 120 分钟；
- 权威记录是 `war_of_desert/赛务记录.json`，`clock.py` 只是选手侧展示；
- 收卷对象是 `workspace/submission/<选手名>_bot.go`，复制到 `submissions/` 并记录 SHA-256、字节数、用时、`accepted`、`missing_submission`；
- 超时仍留档，但 `accepted=false`，不计正式成绩；
- 暂停期间不增长已用时间；重置计时必须保留重开、暂停、收卷历史。

## 9. 回放、复现与审计

每场对阵写一个 `../algorithm-contest/tests/history-seasons/formal-v12/replays/match-NNN.json`：

```text
{ version, match, seed, header, games[
    { index, swap, seed, generator, mapAttempt, rulesHash,
      seats, result, faults, frames, verify, timing }
] }
```

- `header` 是原始 hello，含地图编码，回放不依赖外部文件；
- `frames` 每 5 tick 一帧；终局帧必存；
- `verify` 是引擎用 `orderLog` 重跑整局并逐帧比对的结果。

审计口径：

1. 每个选手的源码哈希与本赛季 `seal-records/<赛季>.json` 一致；
2. 每局 `rulesHash` 一致（第 1 季为 `906f1b14`）；
3. 每局 `verify.ok=true`；
4. `结果.jsonl` 的场次数与 `赛程.json` 一致，缺场必须说明原因；
5. 重跑只允许整场，不允许只重跑某一局。

## 10. 申诉与仲裁

- 申诉窗口：成绩公示后 24 小时。
- 可申诉：裁判执行错误、进程管理错误、赛程错误、结果文件损坏。
- 不可申诉：规则本身、随机地图的具体形状、BT 区间宽度、对手策略。
- 举证责任在申诉方：需指出具体场次、局号、时间点与预期行为。
- 仲裁可做出：维持、整场重跑、判负改判、成绩作废。任何改判必须写入赛季记录并重算 BT。
- 引擎与规则争议以 Go 原生引擎 `internal/sim`（当前 v1.9.2）的实际行为与 `rulesHash` 为准；`engine/golden/` 与 golden trace 是可复现的判据来源。快照 oracle 仅用于第 1 季（v1.0）历史复现。
