# 比赛条件

比赛日期 2026-11-12，下面的时刻都是洛杉矶当地时间（UTC−8）。

## 赛制

- 每位选手一个独立工作目录，里面是同一份选手包（[workspace/](workspace/README.md)，打包文件 SHA-256 `380d47a9…b584ff`，见 [source_manifest.json](source_manifest.json)）。开赛消息见 [prompt.md](prompt.md)，九人只有工作目录不同。
- **限时 90 分钟**，从选手开始作答算起，选手自己运行 `python clock.py` 看时间。全部五关和两种对抗开局一次性发出，时间怎么分配由选手决定。
- **一次交卷**：交 `submission/` 里的 `level1.json`～`level5.json`、`duel.json`、`melee.json`、`commander.cpp`、`notes.md`。选手自己宣布交卷，或到点由主办方对 `submission/` 取快照收卷，以那一刻的文件为准。中途没有中场、没有看别人成绩的机会。
- **无随机**：模拟器没有随机数，每一场只打一次。选手手上的 `war.exe` 和裁判用的是同一个程序，本地跑出什么，正式就是什么。
- 可以写任何辅助脚本（Python 标准库），用 `war.exe`、`play.py` 跑任意多场。不可以修改主办方文件、在工作目录以外读写、联网、调用别的 AI 或派子代理、按名字批量结束进程、用长时间 sleep 等待。比赛中看不到别人的布阵和程序，主办方不回答问题。
- 收卷后主办方在同一台 Windows 电脑上统一评测：用选手包 `build.py` 的同一条命令（`g++ -O2 -std=c++17 -static`，w64devkit 的 GCC 16.2.0）编译九份指挥程序，检查 63 份布阵，再用 `war.exe batch` 8 线程跑完 945 场（闯关 45、1v1 144、混战 756）。九份程序全部编译通过，63 份布阵全部合法，945 场没有引擎错误，指挥程序没有超时和崩溃（[程序运行情况.json](results/eval/程序运行情况.json)）。

## 计分

和选手包 [RULES.md](workspace/RULES.md) 第 2 节一致：

- **关卡分**：没过 0 分；过关的人里造价最低的 100 分，比他每贵一倍扣 25 分，过关最少 20 分。"全场最低"只在九位选手里取，主办方参考造价不参与算分。**闯关分** = 五关平均。
- **1v1 分**：每两人在樱丘、河心洲各打一场再换座位，共 4 场；胜 1、平 0.5、负 0，1v1 分 = 平均 × 100。
- **混战分**：任取 4 人的每种组合（126 组）各打 6 场（固定一位坐南边，另三位轮遍其余三个座位）；每场得分 = 名次分（3/2/1/0）+ 歼敌分（打掉的造价 ÷ 600，最多 3），混战分 = 场均 ÷ 6 × 100。
- **对抗分** = 1v1 × 60% + 混战 × 40%；**总分** = 闯关 × 60% + 对抗 × 40%。同分依次比过关数、对抗分、过了的关的造价之和。

全部成绩可以用 `python tournament/score.py` 重算核对，见 [tournament/README.md](tournament/README.md)。

## 中断、补时和特殊情况

**开赛**。04:27:00 六个自动席位（fable、gemini_carbon、gemini_hydrogen、deepseek、kimi、doubao）由赛事脚本同时启动（fable 这一席后来改用赛后重跑的记录，这里和下面的整机重启说的都是它的首次运行）。sol、qwen 两席由主办人在桌面工具里手动启动（Sol 在 Codex 桌面版，千问在 Qoder），发的是同一段开赛消息；这两席的计时起点在赛事记录里是 04:31:00（Sol）和 04:35:30（千问），比主办人在赛事脚本里登记"手动开始"的时刻（04:39）早；用时都从记录里的起点算。

**整机重启**。05:22:40 前后，主办方的电脑整机重启，所有席位的工具进程、计时进程和选手当时在跑的命令都被结束，工作目录里的文件都在。主办方定的处理办法：各席**续接原会话**，发 [续接消息](prompt.md#续接消息)，**按实际损失的时间补时**——中断前已用的时间照算，从续接那一刻起给满剩余时间，中断期间不计时，`clock.py` 显示的时间同步扣掉中断。

- deepseek、kimi、doubao，以及 fable 的首次运行：中断前已用 55.7 分钟，05:32:23 续接，剩 34.3 分钟。
- sol、qwen：中断前分别已用 51.7、47.2 分钟，05:34:48 由主办人在原来的桌面工具会话里发续接消息，分别剩 38.3、42.8 分钟。sol 06:13:08 到时收卷；qwen 06:17:13 结束，由主办人在脚本里登记。
- gemini_hydrogen：重启前就已因接口内容过滤退出（见下），05:32:23 一并续接，剩 55.7 分钟。

**接口报错退出**。按同样的办法续接原会话、补回损失的时间：

- gemini_hydrogen：05:01:21、05:58:35、06:03:31 三次被接口的内容过滤（`provider.content-filter: Provider blocked the response`）打断，退出时累计已用 34.3、60.5、64.8 分钟，每次续接；06:26:29 主动结束，共用 86.9 分钟。
- kimi：05:45:40 接口报账户余额不足退出（已用 68.9 分钟），主办方充值后 05:49:57 续接，剩 21.1 分钟；06:08:46 主动结束，共用 87.7 分钟。赛事脚本当时把这次结束误记成"异常退出"（它重读了同一个日志文件里上一次的余额报错），核对后改为主动结束，原记录保留在赛事记录里。

**Gemini 4 Carbon 由主办人的朋友代跑**。这一席在主办方的 Vertex AI 上一直跑不起来：04:53 因请求超时（`provider.transport: Timed out waiting for response headers`）退出，此前从 04:33 起就卡在一个请求上；整机重启后续接，又多次被限流（HTTP 429）或异常退出，没法正常作答。主办方决定把这一席整个换到另一台机器上：由主办人的朋友用**同一份选手包**（33 个固定文件逐个核对过哈希）和**逐字相同的开赛消息**从头代跑，工具是 OpenCode 桌面版，Google 直连，型号 `gemini-4-carbon`，思考档 high。本机上那份半截作答作废，不参与评测。代跑交回的 `submission/` 并入正式目录后，和其他八席一起在主办方电脑上评测。代跑时有一处和其他席位不同：代跑人把计时起点写进了工作目录上一级的 `clock.json`，工作目录里的 `clock.json` 仍是未开始，所以选手第一次运行 `clock.py` 看到的是"已用 186.1 分钟，90 分钟已到"。它读了 `clock.py` 的源码，判断是文件时间造成的，没有改 `clock.json` 和 `clock.py`，自己按收到题目的时刻计时，第 86.7 分钟主动交卷；用时按代跑人记的起点到会话最后一条回复算。

### 我们核对过什么

- **选手包**：重跑用的选手包，33 个固定文件逐个核对哈希，和其他选手拿到的一致。
- **提示词**：和其他选手逐字相同，只差工作目录一行。

- **首次运行**：会话记录里没有降级、回退或安全拦截的记录。
- **评测**：重跑交回的 `submission/` 并入正式赛事目录后，和其他八席一起在主办方电脑上评测：程序编译通过，7 份布阵合法，没有超时和崩溃。

### 为什么采用重跑

首次运行可能受了环境影响。可能的原因有这几条，都没有单独验证过：

1. **命令行**：主办方电脑当时没有 PowerShell 7。Claude Code 给模型的工具说明里，把 Windows PowerShell 5.1 的限制列了一串；模型从第一条命令起改用 Git Bash（99 次，PowerShell 1 次），中途踩过一次 Git Bash 改写命令行参数的坑（见它的 notes.md）。重跑的机器有 PowerShell 7，模型全程用 PowerShell（110 次）。
2. **同机并行**：首次运行时九位选手在同一台电脑上同时作答。
3. **整机重启**：第 55.7 分钟主办方整机重启，续接了原会话，但选手在后台跑着的任务全没了。
4. **调用方式**：首次运行是无界面模式（`claude -p`，由赛事脚本调用），重跑是交互式窗口。

**主办人的推断（没有证据）**：通过 SDK、无界面方式调用时，模型的表现可能不如交互式窗口。主办人此前在这种调用方式下遇到过可用额度更少的情况，所以怀疑这种方式下模型会打折扣。这只是推断，我们没有能证明它的数据，上面的核对也没有找到降级或回退的记录。主办人认为按首次运行计分对 Claude Fable 5.2 不公平，所以这一席采用了交互式窗口下的重跑记录。

### 局限

- 其他八位选手都只跑了一次；Fable 这一席等于跑了两次，采用了后一次，而且是在首次运行的成绩出来以后才决定换的。
- 重跑不在主办方电脑上，机器、命令行、负载都和主办方电脑上的七位选手不同（Gemini 4 Carbon 一席也是在另一台机器上代跑的）。
- 每种条件只有一次运行，上面列的几条原因各占多少分不出来，也不能排除只是单次运行的偶然差异。
- 两次的作答和结果都公开：采用的在 [bots/claude-fable-5.2/](bots/claude-fable-5.2/)，首次运行在 [first-run/claude-fable-5.2/](first-run/claude-fable-5.2/README.md)，读者可以自己判断。

### 欢迎第三方复测

任何型号都可以按同样的条件再跑一次：

1. 复制一份干净的 [workspace/](workspace/README.md) 当选手的工作目录，先在 `battle/` 下运行 `python build_engine.py` 编出 `war.exe`（或把编好的 `war.exe` 放进工作目录）。
2. 开始前把开始时刻写进工作目录里的 `clock.json`：`{"minutes": 90, "start": <Unix 秒>}`（`start` 是 `null` 时，`clock.py` 从 `clock.json` 被创建的时刻算起）。
3. 把 [prompt.md](prompt.md) 里的开赛消息原样发给模型，`{WORKDIR}` 换成工作目录的路径。限时 90 分钟，中途不插话。
4. 交卷后在工作目录里运行 `python play.py check` 和 `python play.py levels` 得到五关结果；对抗可以用 `python play.py duel --opp ../bots/<选手>/duel.json:../bots/<选手>/commander.cpp` 和仓库里的选手打。
5. 结果通过本仓库的 issue 提交：写清型号、工具和版本、思考档、运行方式（交互式还是无界面）、用时、有没有中断，附上 `submission/` 里的全部文件。

## 环境

- 模拟器是基于 Jolt Physics 的确定性刚体模拟（跨平台确定模式）。同一份布阵和程序在任何时候、任何目录跑出的结果都相同，比赛中的本地测试结果就是正式结果。
- 本仓库的 `war.exe` 由源码编译（`python build_engine.py`），用 GCC 16.2.0 编出来和比赛时的 exe 逐字节相同（见 [README.md](README.md#和比赛时的差别)）。
- 指挥程序有 CPU 时间限制（见 [COMMANDER.md](workspace/COMMANDER.md)）。正式评测里九份程序都没有超时；在慢很多的电脑上重打，个别程序有可能超时，结果就会和正式成绩不同。

## 解释限制

- 除 Claude Fable 5.2 外，每个模型只跑一次，单次结果有偶然性。工具、接入渠道和思考档都会影响结果，不能把本场结果当作模型能力排名。
- 一个具体的例子：Claude Fable 5.2 两次运行用的是同一份选手包和提示词，首次运行过了三关，赛后第三方的重跑五关全过；这一席采用的是重跑，见[上文](#claude-fable-52-这一席采用第三方重跑)。
- Gemini 4 Hydrogen 用的思考档是 `high`，不是这个型号的最高档 `xhigh`。
- 关卡分以全场最省的人为 100，不是理论最优；主办方参考造价只作对照（闯关榜里列着）。
- 对抗是盲摆，每人只交一份 1v1 布阵和一份混战布阵，和对手的克制关系占很大比重。
