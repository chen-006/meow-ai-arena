# 飞镖乱斗 · 选手笔记（deepseek / player.cpp）

## 1. 程序整体思路

这是一个“先重建现在、再做短程推演搜索”的 bot，核心不是一套固定连招，而是每步
（0.05 秒）把当前真实局面估计出来，然后对几十个候选动作各用裁判同款 `dart::Game`
往前推演约 1.3～1.5 秒，挑评分最高的一个执行，下一步重新评估。

### 1.1 处理 4 步反应延迟：从“看到的世界”还原“现在的世界”

观察里别人和别人的镖是 4 步以前的，自己和自己镖是现在的。程序维护自己每一步的
真实状态、镖状态和实际动作（`Hist hist[128]`）。决策时：

1. 用 `Game(info(), obs)` 建局，但把时间拨回 `t - DELAY`：这时观察到的别人正好是
   那个时刻的真实状态；自己的状态换成历史里同一时刻的记录。
2. 从 `t - DELAY` 开始逐帧重放到 `t`。自己的动作用历史里真实发出的动作（所以自己的
   轨迹是精确的），别人的动作用一个“对手模型”猜：朝最近的敌人靠近/拉开、有镖且在
   6.4 米内就带提前量扔、贴身就挥砍/踢、被飞镖威胁就横移。
3. 重放结束后，再把自己和我的镖强制覆盖成观察里的当前真实值。

这样得到一个“现在”的完整估计：对手的位置、状态、手里的镖、空中的镖、塌陷地图等
都被推进了 4 步。所有后续搜索都从这个重建局面出发。

一个实现细节：模型对手有时会因为不会绕大湖而“自己走进坑”。如果直接按这个推演，
会得到“对手必然自杀”的假胜利，导致自己的决策变形。所以推演里对“非我方角色因
落坑而死”做了回滚：视为模型误差，把他放回上一帧继续（只有被我方飞镖/挥砍/踢造成
的死亡才算数）。这明显改善了决策质量。

### 1.2 候选动作

每一步生成约 20～60 个候选（上限 96）：

- **纯移动**：16 个罗盘方向、停止、保持当前速度、以及用 `path_next` 朝“自己的地上
  镖 / 最近敌人 / 地图中心”的寻路方向。
- **扔镖**：手里有镖且 `free` 时，对每个看得见的敌人，用三种提前量（按重建位置的
  全提前、零提前、半提前）瞄准，再叠加评分最好的 3 个移动方向。扔镖时仍可按 50%
  速度移动，所以移动方向与出手方向分开。
- **近战/挥砍**：对 3.2 米内的敌人，朝其 2 步后的预测位置出刀；另外对所有 2.2 米内
  的敌方飞镖也各生成一个朝飞镖出刀的方向，用来尝试 5.4 节的“挥砍挡镖”。
- **冲刺**：8 个方向 + 朝最近敌人；冲刺途中如果模型里接近到 2.8 米，后续策略会自动
  “冲刺接近战”出刀。
- **召回**：自己的镖在地上时生成，由推演决定值不值得站 12 步。四人局里额外收紧：
  最近敌人 6.5 米内、或场上有敌方飞镖、或自己的镖不到 3.5 米时，不生成召回候选。

### 1.3 推演与评分

每个候选都用 `dart::Game` 精确拷贝局面后向前推演：

- 1v1：30 步（约 1.5 秒）；
- 四人局：26 步；
- 4v4：18 步（8 人每步更贵，主动缩短以留 CPU 余量）。

推演中“我”的后续动作不是继续死按第一步方向，而是一个简单的自策略：镖在地上就
去捡，很近就挥砍/踢，冲刺移动段内接近就接刀，被飞镖威胁就横移，其余沿候选方向
走，并用 1/2/3 米三段前视的局部转向避开已经塌掉的坑。

终局评分（越大越好）：

- 自己死亡：极大的负分；若同时敌人也死光（1v1 平局）会补回一部分。为了在“模型
  认为所有候选都会死”时不至于随便选，按活下来的步数给少量加分。
- 1v1 敌人死亡：+50000，敌人全灭再 +40000；四人局每个敌人死亡 +5000。
- 自己的击杀数增加：+800/个。
- 镖的状态：在手里 +350，飞去/回程 +220，召回飞行 +180，在地上 -250（离得近补回）。
- 脚下格子未来多久塌：12 步内 -2500，40 步内 -500；身体周围 8 个方向 650mm 处是否
  能站，不能站每个 -140。
- 与最近敌人的距离：手里有镖偏好 3.3 米；没镖偏好 5.4 米；**敌方镖在空中时改成
  4.4 米（自己有镖）/6.6 米（自己没镖）**——这条是为了躲“回程镖追着主人飞”的路径，
  是我这里提升最大的一条规则（对中档陪练从约 44% 提到约 65% 胜率）。
- 四人局在自己没镖时额外惩罚身边 2.6 米内的敌人数量；塌陷开始后轻微偏向地图中心。
  另外从第 `COL_START-120` 步起，会给一个“朝脚边仍能活过下一波的格子寻路”的移动
  候选，用来适应没见过的塌陷图（三种形式都开启）。

最后按分数取动作。所有比较都是确定性的，没有随机数。

### 1.4 安全与时限

- 召回引导中如果发现 7 米内还有敌人、或场上有敌方飞镖在飞，会立即给移动取消召回
  （召回引导 12 步不能动，被强敌贴住基本等于死亡）。
- 每步先记 `thread_cpu_100ns()`；如果它不可用（本机实测一直返回 -1），则用
  `steady_clock` 的 100ms 兜底。这个 100ms 只是防止机器卡死导致整步墙钟超时，
  正常步的 CPU 只有约 1～2ms，所以不会因为系统调度而改变决策。移动候选总是先
  评估完，所以即使预算用尽，也会输出一个已经算过的、合法的动作。
- 4v4 的推演长度单独降到 18 步；`check` 里 8 人局单步最多约 1.9～5.3ms（10ms
  预算），1v1/四人局通常 0.6～2.4ms、最多约 2.4ms。
- 推演长度还会在“下一波塌陷之前”截断：如果 `t + H` 会跨过下一波塌陷，就把 H
  缩到塌陷前。另外在拷贝候选之前先调用一次 `base.LM()`，把当前这一步的 live map
  建好，避免所有候选在自己的第一步同时重建地图。否则每个候选的 `Game` 拷贝都会
  重建整张 live map，四人局曾因此出现一次 16.5ms 的单步尖峰；修复后同样对局单步
  最多约 2.0ms，`check` 也没有再报超时。

## 2. 强项与弱项

**强项**

- 当前局面重建 + 引擎精确推演，对“飞镖会不会打中我 / 我的镖能不能打中他 / 冲刺
  会不会落坑 / 塌陷格子能不能站”这类物理问题基本不会算错。
- 对回程镖的规避（敌方镖在空中时主动拉开）效果很好。
- 四人局里比较会利用别人互斗：不主动追杀远敌，保持距离，等别人先出局；在混战中
  抓空手/硬直的人。对三个中档陪练 160 局平均得分 2.04（中档三人 2.47 / 2.21 / 2.12），
  属于中下游；40/80 局的小样本会看到 2.1～2.35 的波动。
- 对弱档稳定获胜（`check` 里 1v1 对 weak 两局全胜、四人局第一）；对中档两次 160 局
  合计 155 胜 162 负 3 平（约 48.7%），80 局样本在 37～45 胜之间波动，40 局一组
  曾 27 胜 13 负——40 局样本的运气成分非常大。

**弱项**

- 对“强档”陪练的 1v1 仍然明显下风：20 局约 1～4 胜。主要原因是强档会在我冲刺
  （固定方向、8 步硬直）时扔镖，也会躲开我按当前速度外推的扔镖。我的对手模型比
  真实强档“笨”，所以推演会高估自己的进攻收益。
- 扔镖命中率不高：强档对局里我方 25 次出手只有 1 次真正命中，大量被空中撞镖、
  被躲开或打墙。赛后在回放里统计：强档 42 次出手命中 19 次；差距主要在对我的移动
  预测，而不只是瞄准。
- 没有显式的草丛埋伏、没有长期（超过 1.5 秒）规划、没有真正的博弈搜索（对手只有
  一个脚本模型，不是“他会怎么应对我”）。
- 4v4 没有队伍协同（不用 MSG、不会主动保护队友），只保证“不主动打队友”。海选
  不计 4v4，所以没有为它做专门优化。
- 冲刺使用偏多（约 4～5 次/局），对强敌是可被利用的破绽；但完全禁用冲刺后对中档
  的胜率会从约 65% 掉到 18%，所以保留了。

**试过但没采用的思路**

- 纯“龟缩跑图”不打人：对强档 20 局 1 胜，自己反而因为往地图边缘跑掉坑 13 次；
  没有平局收益。
- 禁用冲刺 / 禁用召回 / 只在敌人空手时冲刺：对强档略有波动（20 局 1～4 胜，样本内
  不显著），但会显著输给中档；最终保留完整冲刺与召回选项。
- 给“横向移动”加显式奖励：把推演几十点分的细微差别淹没了，对中档从 26/40 掉到
  12/40，放弃。
- 只瞄“重建位置”或只瞄“观察位置外推”：离线用回放做过假设命中率统计，真实当前
  位置直瞄 18/25、观察外推 17/25、全提前只有 12/25；但把瞄准改成直瞄后实战反而
  变差（15/40 对中档），说明推演里对手的躲避模型和真实对手不一致，单纯换瞄准不够。
- “发现连续两次扔空就切保守模式”：对强档没有可测提升，对中档略降，放弃。
- 给冲刺候选加固定分惩罚/奖励、给“敌方飞镖在飞时挥砍”加惩罚、给“敌人硬直时挥砍”加奖励：40 局里都在 22～26 胜之间，和基线 27 胜分不开，且对强档样本仍然只有 0～3 胜；这些手工偏置会盖过推演的细微分差，最终都没有放进正式版本。
- 草丛埋伏（四人局里站在草里且 `expose = 0` 给加分）：40 局平均得分 2.05，比不加的 2.35 差，而且召回次数明显上升，放弃。
- 给召回加 15 步个人冷却，避免取消后马上再引导：1v1 对中档 19/40，比不加的 27/40 差；看来频繁召回虽然危险，但也是这个 bot 恢复镖的重要手段。最后只在四人局加了召回限制（见 1.2），1v1 保持自由召回。
- 四人局“危险时不许召回”（最近敌人 6.5m 内 / 有敌方飞镖 / 自己的镖很近时不召回）：召回次数从约 7 次/局降到 0.5 次/局，对 3 mid 的 80 局得分 2.36 与 2.15（原版同条件约 2.04～2.36），对 3 strong 的 24 局从约 0.8～1.2 提到 1.29。没有明显变差且理论上更稳，最终采用（只改四人局）。
- 硬惩罚“敌人正在召回/被踢晕”：发现机会就冲刺/跑过去砍，40 局对中档 22/40、对强档 2/20，和基线分不开，放弃。
- 只惩罚坑、不惩罚墙（鼓励贴墙挡镖）：对中档 16/40，明显变差；把 8 方向墙/坑惩罚从 140 提到 240 也降到 15/40，说明当前 -140 的“留出逃生空间”比较合适。
- 四人局把击杀/敌人死亡分从 +800/+5000 提到 +2500/+9000：平均得分 2.09，和基线 2.0～2.4 没有区别，说明瓶颈不是“不想杀”，而是“打不中”。
- 把自策略的冲刺接刀阈值从 2800 改到 2000（想晚一点接刀、多冲半步）：40 局 22 胜，无显著差别。
- 四人局推演长度改为 22 步：80 局平均得分 2.05，比 26 步的 2.15～2.36 略差，保持 26。
- 四人局再限制冲刺（最近敌人有镖在手里且在 6.5m 内就不冲）：对 3 strong 的 24 局得分 1.25，与不限制的 1.29 相同，放弃。

`check` 最终一次：每步平均约 0.53ms，单步最多约 2.0ms（8 人局，预算 10ms），
第 0 步最多约 21ms（预算 1000ms）。多次跑下来单步最多在 1.9～5.3ms 之间，
1v1/四人局通常不到 2.4ms。

补充的 4v4 测试（海选不计分，只验证稳定性）：`python match.py team player.cpp --vs strong --games 12`
（我方 4 个同程序对 strong + 3 mid）结果 3 胜 9 负，无超时/崩溃，单步最多约 5.9ms。
4v4 的误伤仍然不少（每人平均 3～5 次/12 局），因为程序没有真正的队友协同；海选
不计这一项，所以没有继续优化。

修复“跨塌陷波重建地图”的 CPU 尖峰后，同样的四人局混合对手测试（我 + strong + mid + weak，
24 局）单步最多从 16.5ms 降到约 2.0ms，没有再出现故障；平均得分 2.38，排在 strong
（3.25）之后、mid/weak 之前。

## 4. 规则疑问 / 对裁判与引擎的观察

- **`thread_cpu_100ns()` 在本机不可用**：按 README 的示例做 CPU 预算保护时，返回的
  差值一直是 0（看起来 `GetThreadTimes` 失败，函数返回 -1）。因此程序实际靠
  `steady_clock` 的 6ms 兜底；这和 README 说的“墙上时钟会把调度时间算进去、不可靠”
  一致，但在本机是唯一能用的保护。如果正式机也一样，建议下届把这个函数的可用性在
  README 里注明，或提供一个跨平台实现。
- **4v4 不计海选分，但 `check` 会强制打一局 4v4**。我最初 8 人局单步最多到 6.1ms，
  已经接近 10ms；把 4v4 推演缩短到 18 步后降到约 3.4ms。建议以后在 README 里明确
  海选程序是否也需要为 4v4 的 CPU 余量负责（目前看是需要，否则 check 可能超时）。
- **“观察里的别人是 4 步前”与“镖的 `age`/`left`”组合起来信息量很大**：如果观察到
  对手在 `S_THROW` 且 `timer = 1`，可以确定他下一步结算时必出镖，且出手方向就是
  观察里的 `ax,ay`；这时提前算好镖的当前真实位置是可行的。这一点规则正文没有明说，
  但用 `Game` 重放可以自然得到，算是合法但容易被忽略的信息。
- **模型对手落坑的问题不是引擎 bug**：`Game(info(), obs)` 里看不见的人是 `unknown`，
  不会动也不会被打中；我一开始直接把它当空气，结果推演里对手会“穿过”草丛。后来
  对看不见的人保留 `unknown`，对已看见但模型推演中落坑的人做回滚，才正常。
- **1v1 同归于尽的判定**：规则说同一步同归于尽 = 平局。我的终局评分对“我死但敌人
  也死”给了正的补偿，但推演里如果双方同时死，`Game::over` 的 winner 不一定是 -1；
  我最后只看存活集合，不依赖 winner，所以没有踩到这个歧义。
- **同一命令、同一组种子，重复跑 80 局结果会在 37～44 胜之间变化**（本机
  `--workers 1`）。地图、种子、动作格式都是确定的，我自己的决策也没有用随机数；
  最可能的原因是陪练程序自己也按墙上时钟/CPU 时间收手，机器忙时它们的选择会变。
  因此本地几十局的胜负差不能当成版本优劣，我最终主要看“机制上是否成立”和多种
  对手下的总体趋势。
- 没有发现 `dart.hpp` 和 `RULES.md` 明显冲突的地方；物理、踢人落坑、冲刺越坑、
  挥砍挡镖的边界行为都与文档一致。唯一觉得容易误解的是“圆心正好压在格线上时
  碰到 2/4 个格子”的规则，工具函数 `cell_of_point` 已经处理，直接用它即可。
