# 第 8 集 · 2v2 简化足球

比赛画面渲染器（回放 → 视频画面）：[renderer/](renderer/README.md)

12 个模型两两组队，各写一个 C++ 球员程序，两个程序组成一队踢 2v2 简化足球。先开 5 分钟战术会议，再开发 40 分钟；中场拿到成绩和本队回放，再开发 40 分钟。下半场开始时新增个人队：每个模型用自己的两份程序组成一队，另打一张个人榜。

本目录使用 **2026-10-29 team2 从中场重赛下半场之后的最终版本**。中场赛 2112 局、终场团队赛 2904 局、个人赛 3264 局，共 8280 局（含对参考队的对局）。只公开团队榜和个人榜；赛时宣布的两项各占 50% 如实保留，存档合并“总分”不公开、不用于另排第三张榜。

- **目录里有什么**：`workspace/` 选手包 · `prompt.md`、`prompts/` 主办方消息 · `packages/` 赛时包和队聊说明 · `bots/` 上下半场代码 · `sparring/` 基准和陪练 · `results/` 团队榜、个人榜和逐局结果 · `replays/` 回放 · `tournament/` 赛程、复算和重打脚本 · `notes/` 赛后复盘回答
- **复现榜单**：`python build_reference.py` 后运行 `python tournament/score.py final`（个人榜：`python tournament/score.py individual --bt`），由逐局数据复算积分；重打对局见 [`tournament/README.md`](tournament/README.md)。

## 规则速览

- 12000×8000 的封闭球场，四角切角，球撞墙反弹；两队各两人，一局 1200 步，进球多的队赢。没有越位、犯规、界外球或角球。
- 每名球员由独立程序控制，每步输出 `AX AY KX KY MSG`：加速度、踢球向量、发给队友的 1 字节消息。消息下一步到达；对手看不到。
- 每人看到的都是自己向右进攻的视角。队内 0/1 号按**种子在赛程中的序号**轮换（s0、s2…由 A 位选手踢 0 号；s1、s3…由 B 位踢 0 号），不是按随机种子的数值奇偶。
- 程序 CPU 预算首步 1000 毫秒、以后每步 10 毫秒；单步超时动作作废，累计 30 次才结束程序。崩溃后该球员保持零动作，比赛继续。赛时程序运行于 Windows AppContainer，不能联网、读写文件或创建子进程（本地复现默认不用这层隔离，见下文"本地运行"）。
- 完整规则见 [RULES.md](workspace/RULES.md)，物理实现以 [soccer.hpp](workspace/soccer.hpp) 为准。基础规则中“也可以照抄”是旧表述；**本期实际开赛消息和组队赛说明明确禁止整份或大段照搬队友代码**，个人队的两份程序也必须自己写。见 [提示词](prompt.md) 和 [判定说明](CONDITIONS.md)。

## 赛制

| 阶段 | 内容 |
|---|---|
| 战术会议 | 两人到齐后 5 分钟，只通过队聊讨论，不写代码、不写文件 |
| 上半场 | 40 分钟，各交 `submission/player.cpp`；可以读队友代码、讨论协议，不能改队友文件、不能整份或大段照搬 |
| 中场赛 | 6 支队伍单循环，并各对基准、中档陪练、陪练；每对 32 个种子 × 换边，2112 局 |
| 中场包 | 全队成绩、本队全部对局回放、复盘工具。比赛时两名队员共享中场包 |
| 下半场 | 开始时宣布“团队 50% + 个人 50%”，新增 `submission/partner.cpp`，再开发 40 分钟。团队 `player.cpp` 编译不过则回退上半场；个人搭档没交或编译不过则用 `player.cpp` 打两个位置 |
| 终场团队赛 | 6 支队伍，每对 44 个种子 × 换边，加对 3 支参考队，2904 局 |
| 个人赛 | 12 支个人队，每对 16 个种子 × 换边，加对 3 支参考队，3264 局 |

**计分**：胜 3、平 1、负 0；得分率 = 积分 ÷（对其他参赛队局数 × 3），依次按得分率、净胜球、总进球排序。参考队不占名次，也不计入积分。BT 实力值另含对参考队的对局：胜 1、平 0.5，基准 = 0，差 400 分约对应 10:1；每对加一局虚拟平局，95% 区间按种子整块重抽样 300 次。BT 不决定本期排名，两张榜的 BT 是各自独立拟合，不能直接相减。本地 `match.py run` 的得分率用胜 1、平 0.5，也不同于正式榜。

## 赛事事故与处理

- **GLM 上半场**接口超时约 16.5 分钟，**DeepSeek 上半场**流空闲约 5 分钟并有传输重试，均不补时。
- **team2 首次下半场作废**：Kimi 遇每日额度上限，Step 遇接口超时。10-29 从中场重赛下半场，上半场和中场仍有效。重赛中 Moonshot 官方接口持续过载，两次按秒补时，共 27 分 25 秒；最后改由**火山方舟提供的同一模型 Kimi K3.1 Pro**完成，最后这一段不是 Moonshot 官方服务。
- **个人赛整体重跑**：主办方沙箱故障导致 Astra 对 DeepSeek 的两局四个程序全部启动失败，却误记为 0:0；整场作废后用新种子重跑，本目录只用最终有效结果。
- 上半场文件审计守护曾停摆，之后补扫和补核；缺少记录不能当作没有操作。人工粘贴的三位选手下半场消息晚到约 1.7～1.9 分钟，未补时。细节见 [CONDITIONS.md](CONDITIONS.md)。

- **未读消息提醒未完整接入**：选手[队聊说明](packages/TEAMCHAT_README.md)原文是“编译、跑对局、复盘等工具输出末尾**如果出现**”未读提醒，则应查看消息，这是条件句。实现上只有看表工具 `clock.py` 接入提醒，`build.py`、`match.py`、`replay.py` 没有接入；所有选手使用同一套工具。

## 马上看 / 马上玩

**看回放**：直接打开 [viewer.html](workspace/viewer.html)，拖入 [回放目录](replays/README.md) 中任一 `.txt`，无需联网。18 局按固定种子随机抽样，不按胜负或比分挑局。

**自己开发或对战**（Windows、Python 3.10+、g++；无需第三方 Python 包）：

```text
python build_reference.py
cd workspace
python match.py check template.cpp
python match.py run --me template.cpp --mate template.cpp --opp baseline --seeds 2 --workers 1
python match.py play ../bots/half2/team4_a.cpp ../bots/half2/team4_b.cpp baseline baseline --seed 3
```

编译器可放进仓库的 `tools/w64devkit/bin/`，或加入 PATH，或设置 `CXX`。参照程序从源码编译。本地对战和重打默认不做身份隔离（`--sandbox none`）：每步 CPU 预算、超时强杀、内存 1 GB、不能开子进程仍由裁判的 Job Object 照常限制，结果与赛时规则一致；想按赛时环境复查，给 `match.py` 或 `reproduce.py` 加 `--sandbox appcontainer`。裁判 `arena.cpp` 直接调用 Windows API，目前只能在 Windows 上运行。完整用法见 [workspace/README.md](workspace/README.md)。按原种子和座位重打一局、复算榜单见 [tournament/README.md](tournament/README.md)。

## 和比赛时的差别

- 封存代码逐字节原样，包含换行符。基础选手包除下述适配外保留原文；`build.py` 只把主办方私有目录的编译器探测改成仓库 `tools/w64devkit`。陪练头文件只调整了引擎 include 相对路径。另为 `match.py` 自动重建裁判的命令补上 `-luserenv`（原包自带 exe，缺少这个链接库会导致从源码构建失败）。本次另移除裁判的固定绝对沙箱备用目录，只保留显式 `SOCCER_BOX_ROOT` 或裁判相邻目录；`match.py` 检测裁判源码/引擎头文件更新后重建缓存，选手包说明同步改写。`match.py` 和 `tournament/reproduce.py` 默认给裁判传 `--sandbox none`（赛时是 AppContainer；复现成绩不需要防越界，也免得被杀毒软件拦住沙箱目录），可用 `--sandbox appcontainer` 切回。所有适配记在哈希清单里。
- 裁判的沙箱改为循环复用固定名额 `soccer2v2.<根目录标记>.s<k>`（标记是沙箱根目录路径的 SHA-256 前 128 位），不再每局用新名字 `soccer2v2.<进程号>.<序号>`。Windows 为每个新出现的 AppContainer 在内核里留一份记录（池标签 `SeLs`），删除沙箱后也要到重启才释放；连续打几万个沙箱后，`CreateProcess` 会报错 1450（系统资源不足），只能重启。复用名额后这份记录不再随局数增长；被强行结束的裁判留下的沙箱目录和配置，也会在这个根目录下次占用该名额时清掉；名字带根目录标记，别的根目录里的选手程序拿不到同一个身份，读不到这些残留的程序副本。选手进程也改为创建时就放进 Job（原来是先挂起创建、再放进 Job），裁判在这两步之间被强行结束时不会再留下一个一直挂起、占着程序副本的选手进程。沙箱的限制、比赛结果和回放不变。
- 比赛时只提供三个参考 bot 的可执行文件，开源版提供源码及编译入口，不提交 exe。不同编译器产物不保证字节相同。不要把含陪练源码的本目录直接当作赛时选手包。
- 主办方计时、封存、启动会话、账号/代理配置、权限审计和队聊服务不收录；提示词里的 `tc.py` / `clock.py` 仅记录历史流程，本目录不能直接自动举办原赛事。完整赛时文件清单、固定文件哈希、动态配置边界和中场包还原步骤见 [还原说明](packages/restore.md)。可还原中场成绩及对局清单，缺少的历史回放可重打，但不保证逐字节相同；没有另存完整重复材料。
- 原 `results.json` 和赛程改用 gzip 存储，机器路径改为以 `soccer/` 为根的相对来源或 `<build>` 占位；其余统计、种子、座位和哈希保留。回放路径指历史完整回放集合，仓库仅保留抽样子集，其他局可重打。
- 不收录任何原始会话日志、队伍聊天导出、思考内容、贡献归属报告、内部分析报告、作废比赛材料、密钥或私人配置。复盘是赛后直接回答，代表模型自述，不能当作已验证事实。team4 的两段回答已按 10-29 修复后重新汇总的新复盘收录。
