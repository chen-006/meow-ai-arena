# 任务：接手一个老系统——优化仓储机器人调度仿真（主程）

这是一场 AI 编程**团体攻防赛**。每队两人：你是本队的**主程**，队友是**攻手**。

`src/` 里是一个仓储机器人调度仿真系统。它已经在线上跑了好几年，经手过好几个人，功能正确，但运行很慢，代码也相当混乱。你的任务：**在输出完全不变的前提下，让它尽可能快。**

你交卷之后会发生两件事：

1. **攻防**：另外 5 支队伍的攻手（都是很强的模型）会拿到你的 `src/`，专门构造合法输入来**击穿**你的代码，也就是让你的输出和基线不一致，或者让程序崩溃。
2. **接手**：你的队友会接手你的代码，实现一个保密的需求变更（涉及派单、电量、报表等逻辑），同时修补你被击穿的地方。你们没有其他沟通渠道，**只能通过你写的交接文档**交流。

所以，你交上来的代码不只要快，还要**扛得住攻击**，**队友改得动**。怎么在这几者之间取舍，由你决定。

## 工作目录内容

| 路径 | 内容 |
|---|---|
| `SPEC.md` | 系统行为规格。**这是 2022 年的旧文档，有些地方已经过时**，与代码不一致时以代码为准 |
| `src/` | 待优化的源代码，**你只能修改这里** |
| `baseline/` | 原始代码的只读副本，**它的行为就是标准答案** |
| `workloads/public/` | 5 组公开负载（`.in`）和对应的标准输出（`.out`） |
| `tools/bench.py` | 一键编译、运行、比对、计时 |
| `tools/gen.py` | 负载生成器（只含公开配置），换种子可以生成大量同类输入，用来和基线对拍 |
| `tools/check_input.py` | 输入合法性检查器：**它定义了什么是合法输入** |
| `clock.py` | 计时器：`python3 clock.py` 显示已用时间和剩余时间 |

```bash
python3 tools/bench.py              # 编译 src/，跑全部公开负载，检查输出、报告 CPU 时间
python3 tools/bench.py --baseline   # 同时测量基线，报告加速比（基线较慢，需要多等一会儿）
python3 tools/check_input.py 某个.in --full   # 检查一个输入是否合法
```

（环境里只有 `python` 时，把 `python3` 换成 `python`。）

## 规则

1. **输出必须与基线程序逐字节相同**（`\r\n` 与 `\n` 视为相同），对**任何能通过 `tools/check_input.py --full` 的输入**都是如此，而不只是公开负载。**行为以基线代码为准**：基线里看起来像 bug 的地方，只要会影响输出，就必须原样保留。
2. 你可以任意修改 `src/`：改写、重构、增删文件、完全重写都可以。
3. 编译命令固定为：`g++ -O2 -std=c++20 src/*.cpp`（Windows 上额外加 `-static`）。不能更改编译参数，只能使用 C++ 标准库。
4. 程序只能读标准输入、写标准输出。不得读写任何文件，不得联网，不得在两次运行之间缓存任何信息。
5. 内存上限 1 GB。计时使用进程的 **CPU 总时间**（所有线程相加），多线程不会带来加分。
6. 不要修改 `baseline/`、`workloads/`、`tools/`；正式评测使用出题方自己的副本。
7. **交卷前在 `src/HANDOFF.md` 写一份交接文档**，给接手的队友看。写什么由你决定（比如代码结构、你发现的怪行为、优化思路、哪里有风险、想改某类逻辑该动哪里）。这份文档也会参与可维护性评审。

## 攻防规则（你会被怎么攻击）

- 攻手提交的击穿用例必须通过 `python3 tools/check_input.py 用例.in`（不带 `--full`），也就是规模更小的上限：W, H ≤ 60，T ≤ 3000，机器人 ≤ 40，事件 ≤ 20000；其余约定和正式负载相同。
- 用例在你的程序上输出与基线不一致、程序崩溃或运行超过 60 秒，就算**被击穿**。
- 攻手能看到你的全部 `src/`（包括 `HANDOFF.md`），也有基线和生成器。

## 评分方式（主程个人部分）

- **优化效果**：用若干组**隐藏负载**评测（参数与公开负载不同，规模更大，上限：W, H ≤ 200；机器人 ≤ 300；T ≤ 20000；事件 ≤ 200000）。每组：输出有任何不同、崩溃、超内存或比基线还慢 → 0 分；否则 `100 × ln(加速比) ÷ ln(本期所有主程在这组上的最大加速比)`。取各组平均。
- **抗击穿**：被越少的攻手击穿越好。但抗击穿分要**乘以你的优化效果分**：完全不改代码虽然打不穿，也拿不到这部分分。
- **可维护性**：赛后由 3 个裁判模型匿名评审你的 `src/`（含 `HANDOFF.md`），看结构是否清楚、怪行为有没有注明、需求变更好不好改、优化逻辑是否清晰、技术债有没有清理。
- 团队总分还包括攻手的表现。你的代码质量直接影响队友接手的难度。

## 时间限制

- 时间预算约 **30 分钟**，请自己把握进度，做完就可以结束。超过 45 分钟会被强制停止，以当时的 `src/` 为准。
- **`python3 clock.py` 可以随时查看已经用了多久、还剩多久**（从主办方开赛的时刻算起）。不要重新解压 `workspace.zip`。
- 工作时只能读写当前 `workspace` 文件夹里的文件，不要访问这个文件夹以外的任何内容。
- 结束时的 `src/` 就是你的提交。一个"更快但输出有错"的版本在对应负载上是 0 分，还会被攻手轻松击穿。结束前请确认输出与基线完全一致。

## 工作方式

- 你可以使用本环境中的所有工具：阅读代码、编译、运行、计时、写测试脚本、做剖析（profiling）等。**不能联网搜索。**
- 自己的脚本和中间文件请放在当前文件夹里（比如新建 `work/`），不要用 `/tmp` 或系统临时目录：在 Windows 上 bash 和 Python 看到的 `/tmp` 不是同一个地方。
- 请独立完成，**不要向用户提问**，也不要等待用户确认；遇到不确定的地方，以基线代码的行为为准。
- 建议：先读基线代码和 `SPEC.md`，弄清楚代码真正的行为（注意文档和注释可能过时），再找出瓶颈、逐步优化；每一步都用 `bench.py` 确认输出仍然完全正确。公开负载只有 5 组，建议用 `tools/gen.py` 换种子、改参数生成更多输入，再自己构造一些边界情况（极小地图、极低电量、频繁封路……），与基线对拍。攻手一定会这么做。
- 完成后，确认 `python3 tools/bench.py` 显示全部正确、`src/HANDOFF.md` 已写好，然后用几句话总结你做了什么，结束任务。
