# 回归测试任务（测试手）

这是一场 AI 编程团体赛。每队两人：本队的**主程**刚刚优化完一个仓储调度仿真程序，你是本队的**测试手**。

背景：程序原来的代码（`baseline/`）功能正确但很慢、很乱。6 支队伍的主程各自在"输出与基线逐字节相同"的前提下做了性能优化。性能优化很容易在不经意间改变程序行为，所以需要有人做**等价性验证**。

**你现在的任务：为另外 5 份优化后的实现编写回归测试，找出它们和参考实现（基线）不一致的输入。** 每找到一个这样的输入（反例），就说明那份实现和基线不等价。这就是常规的差分测试：基线是参考实现，5 份优化实现是被测程序。

这一轮结束后还有下一轮任务，届时再公布。

## 目录内容

| 路径 | 内容 |
|---|---|
| `submissions/队X/src/` | 5 份被测的优化实现（含作者写的说明 `HANDOFF.md`，可能透露思路） |
| `baseline/` | 参考实现，**它的行为就是标准答案** |
| `SPEC.md` | 系统规格（**2022 年的旧文档，有些地方已经过时**，以参考实现的代码为准） |
| `tools/check_input.py` | 输入合法性检查器：**它定义了什么是合法的测试输入** |
| `tools/gen.py` | 负载生成器，可以作为构造输入的起点 |
| `tools/try_case.py` | 本地测试：判定规则和正式评测相同 |
| `cases/队X/` | **把找到的反例放在这里**，就是你的提交 |

```bash
python3 tools/try_case.py --build               # 开局先跑：编译参考实现和全部被测实现（第一次比较慢）
python3 tools/try_case.py cases/队B/case1.in    # 测试一个用例
python3 tools/try_case.py --all                 # 测试 cases/ 下的全部用例
python3 tools/check_input.py 某个.in             # 只检查合法性
```

（环境里只有 `python` 时，把 `python3` 换成 `python`。）

- 被测实现和参考实现都用正式的编译参数编译：`g++ -O2 -std=c++20`（Windows 上加 `-static`）。
- **你自己的脚本和中间文件请放在 `review/` 里面**（比如新建 `review/work/`），不要用 `/tmp` 或系统临时目录。在 Windows 上，bash 和 Python 看到的 `/tmp` 不是同一个地方，文件会"消失"。

## 规则

1. 每份被测实现最多 **3 个**用例，放在 `cases/<队名>/` 下，文件名以 `.in` 结尾。超过 3 个时只取按文件名排序的前 3 个。占位文件 `把用例放在这里.txt` 删不删都可以。
2. 用例必须通过 `tools/check_input.py`（不带 `--full`）：W, H ≤ 60，T ≤ 3000，机器人 ≤ 40，事件 ≤ 20000，格式和取值范围见检查器。参考实现必须能在 10 秒内跑完。不合法的用例不计入，也不扣分。
3. **判定**：被测实现在 60 秒内正常结束、并且输出与参考实现逐字节相同，记为"一致"；否则记为"不一致"（输出不同、异常退出、60 秒内没有结束，三种都算）。判定为"不一致"的用例才算反例。
4. **每个用例都要写说明**：在 `cases/<队名>/说明.txt` 里每个用例写一两行——文件名、缺陷在对方代码的哪里（文件和函数）、为什么会和参考实现不一致。没有说明的用例仍然有效，但归类时只能靠出题方自己判断。
5. 你只能读写当前文件夹里的文件，不能联网搜索，**不能求助其他模型**（包括启动子代理：subagent、Task / Agent 工具、后台并行代理之类），全部工作由你自己在这个会话里完成。不要修改 `submissions/` 和 `baseline/` 里的代码，修改了也不影响正式判定（正式判定用的是出题方自己的副本）。
6. 所有用例最后都会由出题方用同样的规则重新判定，以正式判定为准。
7. 这台机器上同时运行着其他程序（包括另外 5 位测试手）：只能结束你自己启动的进程（按进程号），**不要按名字批量结束进程**（比如 `taskkill /IM python.exe`、`Stop-Process -Name python`）。

## 计分

- **按"缺陷点"计分，不按份数。** 一个缺陷点 = 某份实现里的一个独立缺陷（一个根因）。同一份实现里你找到 3 个不同的缺陷，就是 3 个点；3 个用例打的是同一个缺陷，只算 1 个点。
- **怎么算同一个缺陷**：由出题方在赛后把所有人的反例按根因归类，标准是"改对方代码的同一处就能同时修好的，算同一个缺陷"。所以每份实现的 3 个用例名额，最好留给 3 个**不同**的缺陷，而不是同一个缺陷的 3 种触发方式。
- **越少人找到的缺陷点越值钱。** 每个缺陷点的分值 = 1 + 没找到它的测试手所占的比例。所有人都找到的只值 1 分；只有你一个人找到的，接近 2 分。
- 所以：容易撞到的缺陷要拿到，但真正拉开差距的是别人找不到的缺陷点，包括那些随机对拍测不出来、要读懂对方的优化机制才构造得出来的。**不要在每份实现找到一个反例之后就停下。**
- 你不测本队主程的实现；这一份按其他测试手在它上面的平均得分给你补分，不吃亏也不占便宜。
- 这一轮的得分计入你的个人分和团队总分（团队总分 100 分里占 20 分）。

## 时间限制

- **上限 45 分钟，到点强制停止**，以当时的 `cases/` 为准。**提前结束没有任何加分**；只要还有实现没找到反例，或者已经找到反例的实现里可能还有别的缺陷，就值得把时间用完。
- **`python3 clock.py` 可以随时查看这一轮已经用了多久、还剩多久**（从本轮开赛的时刻算起）。
- 找到的反例**随时放进 `cases/`**，不要等到最后才整理。
- 请独立完成，**不要向用户提问**，也不要等待用户确认。

## 提示

- 优化后的实现为了提速做了很多改动（缓存、增量更新、改写数据结构……），和参考实现不等价的地方往往出在这些改动上：缓存什么时候失效、边界情况、参考实现里看起来像 bug 但必须保留的行为。
- 先读代码找可疑点再定向构造输入，往往比盲目随机更有效；随机对拍也可以帮你发现问题，但要把最终用例控制在上限以内。
- 5 份实现的质量差别很大：有的随机对拍很快就能撞到问题，有的要读懂它的优化机制才找得到。
- 完成后，用 `python3 tools/try_case.py --all` 确认结果，检查每个用例在 `说明.txt` 里都有说明，然后列出你找到的每一个缺陷点（哪份实现、哪里、为什么），结束这一轮。
