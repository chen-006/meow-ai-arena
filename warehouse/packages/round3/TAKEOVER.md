# 接手任务（测试手 · 第 3 轮）

上一轮的回归测试结束了。现在轮到你**接手本队主程的代码**。

`workspace/src/` 里是本队主程交上来的代码，`src/HANDOFF.md` 是主程写给你的交接文档。

**这一轮主要考你的优化能力**：需求变了以后，你最终交出来的程序在大规模负载上能跑多快。改对是前提，跑得快才是主要得分项。三件事按顺序做：

1. **修复**：`workloads2/regression/` 里是上一轮别队找到的反例（本队主程代码在这些输入上和基线不一致）。修好它们。
2. **实现需求变更**：见 `CHANGE.md`。
3. **优化（重点）**：让变更后的程序在大规模负载上尽可能快。需求变更会让主程原来的一些优化失效（比如按固定优先级排好序的结构、缓存的派单结果），直接套上去往往"能对但很慢"，需要你重新设计。

## 你的权限

- `src/` 你可以任意修改：小修、大规模重构、完全重写都可以。
- 主程的代码如果实在没法救，也可以**从 `baseline/` 重新开始**（`baseline/` 是原始的屎山代码，行为就是标准答案）。

## 目录内容

| 路径 | 内容 |
|---|---|
| `CHANGE.md` | 需求变更，**请仔细阅读** |
| `src/` | 本队主程的代码 + `HANDOFF.md`，**你只能修改这里** |
| `baseline/` | 原始基线代码（变更之前的标准行为） |
| `SPEC.md` | 2022 年的旧规格文档，有些地方已经过时，以基线代码为准 |
| `workloads2/public/`、`workloads2/edge/` | 变更后的 4 组小型公开负载和 30 个边界用例（带标准输出）：**用来查对错，规模太小，看不出快慢** |
| `workloads2/big/` | **3 组接近正式规模的大负载（带标准输出），用来看快慢**；`reference_cpu.json` 是未优化的参考实现在这台机器上的 CPU 时间 |
| `workloads2/regression/` | 本队的回归用例：上一轮找到的反例（带标准输出） |
| `tools/bench2.py` | 编译 `src/`，跑用例，逐字节比对；加 `--big` 跑大负载并显示加速比 |
| `tools/gen2.py` | 生成更多变更后格式的输入（没有标准输出），包括大负载的配置 |
| `tools/check_input.py` | 合法性检查器；加 `--p2` 检查新格式 |
| `workloads/public/`、`tools/bench.py` | 变更前的公开负载和工具，可以用来对照基线的老行为 |

```bash
python3 tools/bench2.py              # 查对错：小型公开负载 + 边界用例 + 回归用例（几秒）
python3 tools/bench2.py --big        # 看快慢：3 组大负载，显示相对参考实现的加速比（和正式评分同一种算法）
python3 tools/bench2.py --skip-edge  # 只跑 4 组小型公开负载
```

（环境里只有 `python` 时，把 `python3` 换成 `python`。）

**关于大负载**：`--big` 显示的"加速比" = 参考实现的 CPU 时间 ÷ 你的 CPU 时间。参考实现是一份干净但完全没有优化的写法，所以加速比是 1 倍左右说明你的程序基本没有优化。正式评测的隐藏负载和这 3 组规模相当或更大（T 最大 12000），参数不同，种类更多（还有低电量、长时间、混合型）。超过参考实现用时 3 倍加 10 秒的，正式评测判超时。

**关于测试耗时**：`bench2.py`（不带参数）每次几秒到十几秒，可以放心多跑。`--big` 对已经优化过的代码每次十几秒；某一组比参考实现还慢时会提前中止这一组（参考实现三组分别要 34、68、128 秒左右），所以代码还很慢时不要反复跑全套，用 `--only p2_big_flood` 先看最短的一组。自己写随机对拍时注意：`baseline/` 很慢，用例规模要小。

**关于回归用例**：它们原本是旧格式。转换时在 `PARAMS` 行末尾加了 `agingEvery=1000000000`、`carryCost=1`。在这两个取值下需求变更不起作用，所以它们检验的就是原来那个缺陷有没有修好。标准输出和原用例相比只多了报表里的 `aged=0`。没有这个目录或目录为空，说明上一轮没有人找到本队主程代码的反例。

回归用例里可能有**性能型反例**（文件名或上一轮的判定是超时）：主程代码在这种输入上输出没错，但比基线慢很多，60 秒内跑不完。这类也要修——修好的标准是 60 秒内结束且输出正确，`bench2.py` 对回归用例按 60 秒限时。它们通常指向主程某个优化在特定输入下的性能退化，修的时候顺便想想大负载上有没有同样的问题。

注意：主程的原代码只认识旧的输入格式，所以刚接手时跑 `bench2.py` 很可能全部报错。这是正常的，实现了新格式以后才会逐渐变对。

## 规则

- 变更后的程序只需要处理**新的输入格式**（`PARAMS` 行多两个数）。对任何能通过 `tools/check_input.py --full --p2` 的输入，输出都必须和"基线 + CHANGE.md"的行为逐字节相同。
- 编译命令、只用标准库、只读标准输入写标准输出、CPU 计时（多线程不加分）、1 GB 内存等规则和之前相同。
- 只能读写当前文件夹里的文件，不能联网搜索，**不能求助其他模型**（包括启动子代理：subagent、Task / Agent 工具、后台并行代理之类），全部工作由你自己在这个会话里完成。
- 这台机器上同时运行着其他程序（包括另外 5 位测试手）：只能结束你自己启动的进程（按进程号），**不要按名字批量结束进程**（比如 `taskkill /IM python.exe`、`Stop-Process -Name python`）。
- 自己的脚本和中间文件请放在当前文件夹里（比如新建 `work/`），不要用 `/tmp` 或系统临时目录：在 Windows 上 bash 和 Python 看到的 `/tmp` 不是同一个地方。

## 评分

团队总分 100 分里，这一轮占 50 分：

| 分项 | 团队权重 | 怎么算 |
|---|---|---|
| **接手速度** | **20** | 变更后的隐藏负载，每组：输出有任何不同、异常退出、超时 → 这一组 0 分；否则 `100 × ln(加速比) ÷ ln(这一组全场最大加速比)`，加速比相对参考实现。取各组平均 |
| 接手正确 | 20 | 隐藏负载输出正确的比例（占 3/4）+ 本队回归用例修好的比例（占 1/4） |
| 可维护性 | 10 | 赛后由裁判模型匿名评审你最终的 `src/`（含 `HANDOFF.md`） |

你的**个人榜**另外看两项速度：一是上面的接手速度（终点有多快）；二是**增值**——正式负载和主程那一轮的隐藏负载是同一批地图和事件（只多了两个新参数），所以直接比较：同一组数据上，你的终版比主程交卷时的版本快了多少倍。主程的代码已经很快时，增值空间小，但接手速度的起点高；主程的代码慢时反过来。两项各占个人榜的 20%。

- **速度分是和全场最快的比，按对数计分**：别人优化了 50 倍而你只做到 5 倍，这一项就只有四成左右。只把需求变更做对、不做优化，接手速度和增值都接近 0。
- **正确是门槛**：一个"更快但输出有错"的版本，在出错的负载上速度分是 0。每做完一步优化都用 `bench2.py`（不带参数）确认还是全部正确，再用 `--big` 看效果。
- 建议在 `src/HANDOFF.md` 末尾补一段：你改了什么、现在的优化机制和它的失效条件。

## 时间限制

- **上限 45 分钟，到点强制停止**，以当时的 `src/` 为准。**提前结束没有任何加分。**
- 建议的节奏：先用尽量短的时间把修复和需求变更做对（跑通 `bench2.py`），**剩下的时间都用来优化**，最后留 5 分钟做一次完整确认。只要 `--big` 的加速比还有明显提升空间，就值得继续。
- 到点时 `src/` 里是什么就交什么，所以**不要让 `src/` 长时间停在编译不过或输出有错的状态**；大改之前先留一份能通过的副本（放在 `work/` 里）。
- **`python3 clock.py`（在 `workspace/` 里）可以随时查看这一轮已经用了多久、还剩多久**（从本轮开赛的时刻算起）。
- 请独立完成，**不要向用户提问**，也不要等待用户确认。
- 完成后，确认 `python3 tools/bench2.py` 全部正确，报告 `--big` 的三个加速比，然后用几句话说明你是怎么改的（包括有没有大改或重写、做了哪些优化、为什么），结束任务。
