## 一、 系统架构与文件职责

源码统一组织在 `src/` 目录下，编译命令固定为 `g++ -O2 -std=c++20 src/*.cpp`（Windows 下自动带 `-static`）。

1. **`common.h`（公共头文件与紧凑数据结构）**
   - 定义了全局网格参数（`W, H, T`）与常量（`BIGNUM = 1000000000`）。
   - 定义核心实体结构体：
     - `Robot`：包含坐标 `(x, y)`、电量 `battery`、目标 `(target_x, target_y)`、等待计数、状态枚举 `state`、绑定订单等。
     - `Order`：包含起止坐标、优先级、到达时刻、状态枚举 `status`、分配机器人等。
     - `Event`：紧凑事件结构体，解析时一次性按顺序存储。
   - 内联辅助判定函数：`INMAP`（越界检查）、`ISWALL`（货架墙体）、`OK`（是否可通行：在图内、非墙且未被封锁）、`OCC`（格子是否被其他非 DEAD 机器人占据，$O(1)$ 查找）。

2. **`sim.cpp`（仿真主调度引擎）**
   - `ReadAll(istream& in)`：输入读取与预处理。
     - **特别注意**：已实现对 `PARAMS` 的变长安全解析。二阶段传入 8 个参数时会自动存入 `PRM[6]`（`agingEvery`）和 `PRM[7]`（`carryCost`），无需重写解析器。
   - `RunSim()`：每个 tick 核心流水线（严格遵循基线时序）：
     - **阶段 1（事件）**：$O(1)$ 游标推进处理当前 tick 的订单、取消、封路与解封事件。
     - **阶段 2（救援）**：停机滿 100 tick 且当前位置无车占用的机器人复活（半电，详见下文怪异行为）。
     - **阶段 3（充电）**：充电中机器人充至 90% 即出发。
     - **阶段 4（派单）**：高电量空闲车与待派单匹配。带有高效的**候选机器人早停剪枝**。
     - **阶段 5（低电量寻桩）**：寻找可用或最近充电桩。
     - **阶段 6（机器人移动与避障）**：多车协同移动、连续等待 4 步后的侧移避让、到达目标处理。
     - **阶段 7（报表与热点监测）**：周期性输出各状态统计及曼哈顿热点中心。
   - `Finish()`：输出总结、平均延迟四舍五入除法与所有机器人最终状态。

3. **`util.cpp`（算法与高性能工具库）**
   - `get_cached_bfs(sx, sy)`：基于网格版本号（`grid_version`）的环形 BFS 距离场缓存。当且仅当发生有效 `BLOCK`/`UNBLOCK` 时版本号递增。命中率 > 95%，单次 BFS 耗时 < 5 微秒。
   - `ensure_chg_dist()` / `get_chg_dist(x, y)`：全图多源充电桩 BFS 距离场预计算。单次计算只需 $O(W \times H)$，派单时查询送货点到充电桩距离为 $O(1)$。
   - `compute_hotspot(hx, hy, hc)`：**曼哈顿菱形热点统计**。采用将 $\|(x,y)\|_1$ 旋转 45 度的坐标系映射（$u = x+y, v = x-y$），将任意半径的菱形转化为轴对齐矩形，利用 2D 差分 + 前缀和实现严格 $O(NR + (W+H)^2)$ 耗时（$\le 0.1\text{ ms}$），完全免疫超大 `hotRadius` 或高密度攻击。
   - `writeLog` / `writeRaw` / `dumpLog`：64MB 预分配高性能字符串输出缓冲，彻底消除基线反复分配单个小字符串的系统开销。

4. **`old_stuff.cpp`**
   - 历史无用废弃逻辑与未生效的旧派单已全部清除，避免产生技术债与干扰。

## 二、 关键基线怪异行为（Bug-for-Bug 行为对照，切勿修改！）

基线代码中存在多处与 `SPEC.md` 或常理不符的“历史特性”，出题方评测是以 `baseline/` 为绝对标准。以下行为已在代码中精准复刻，**请务必注意不要“顺手修掉”**：

1. **派单同距离平局规则（最大陷阱）**：
   - `SPEC.md` 和旧注释都写着“选编号小的”。
   - 但基线实际实现为 `if (a <= best) { best = a; who = i; }`。
   - 机器人在循环中按编号 $i = 0 \dots NR-1$ 遍历，由于使用的是 `<=`，当两台车距离相等时，**后遍历到的（编号更大的）机器人会覆盖前者**！
   - 攻手如果构造等距用例攻击，必须保证编号大者胜出。我们的代码严格维持了 `if (a <= best)`。

2. **救援复活并非满电**：
   - `SPEC.md` 写着“电量充满”，基线实际代码为 `RB[i] = PRM[0] / 2;`（只恢复 50% 电量）。

3. **充满电提前离开**：
   - `SPEC.md` 写着“达到 batteryMax 时变为 IDLE”，基线实际代码为 `if (RB[i] * 10 >= PRM[0] * 9)`（电量达到 90% 即算充满出发）。

4. **平均延迟的四舍五入除法**：
   - 统计总结中的 `LATENCY avg` 使用公式：`(CNT[4] + CNT[0] / 2) / CNT[0]`（这是整数实现的四舍五入除法，并非向零截断整除）。

5. **CANCEL 事件计数器 `CNT[3]` 的统计时机**：
   - 只要订单号存在，哪怕由于订单已经在 `PICKED` 或 `DONE` 状态导致取消失败输出 `CANCEL_FAIL`，基线依然执行了 `CNT[3]++`。

6. **BFS 起点无视可通行检查**：
   - 基线规范规定：BFS 起点 `(sx, sy)` 自身无论是否被墙阻挡或封锁，初始距离都设为 0；只有后续走的邻居格子才需要满足 `OK`。当一台机器人所在格子被意外 `BLOCK` 时，它依然可以向四周合法相邻格走出。

## 三、 第二阶段需求变更指南（保密需求应对建议）

根据对测试验证器 `tools/check_input.py --p2` 的逆向分析，第二阶段的输入在 `PARAMS` 行末尾追加了 2 个参数：
```
PARAMS batteryMax chargeRate lowThreshold safetyMargin reportEvery hotRadius agingEvery carryCost
```
即：
- `PRM[6]`: `agingEvery`（范围 $1 \dots 10^9$）
- `PRM[7]`: `carryCost`（范围 $1 \dots 100$）

如果你接手后的需求变更与这两个参数相关，建议定位到以下位置直接扩展：

### 1. 如果 `carryCost` 表示“载货时的移动耗电”
- **移动位置**：`sim.cpp` 阶段 6（机器人移动逻辑）：
  - 机器人在移动时扣电代码为 `ROBOTS[i].battery--;`。
  - 若为载货状态（`ROBOTS[i].state == STATE_DELIVERING`），可改为：
    `ROBOTS[i].battery -= (1 + PRM[7]);`（或需求指定的耗电公式）。
- **派单电量校验位置**：`sim.cpp` 阶段 4（派单评估）：
  - 订单评估中的送货耗电原本是 `b = calc_dist(px, py, dx, dy)`。
  - 若载货耗电增加，可将送货段所需电量从 `b` 调整为 `b * (1 + PRM[7])`（按需求公式适配）。

### 2. 如果 `agingEvery` 表示“电池周期性老化/容量衰减”
- **触发位置**：`sim.cpp` 主循环 `for (int t = 0; t < T; t++)` 开头或末尾：
  - 判断 `if ((t + 1) % PRM[6] == 0)`。
  - 在此处更新最大电量上限或衰减当前电池电量。

## 四、 核心优化点与安全保障

1. **事件推进**：事件预处理在读取时解析完毕，主循环采用单指针推进，复杂度由 $O(T \times E)$ 降至 $O(E)$。
2. **多源充电场**：充电桩距离预计算后单次派单只要 $O(1)$，彻底避免基线每个订单对每台车重复进行全图 BFS 的灾难。
3. **派单候选剪枝**：如果当前可用候选机器人数为 0，直接跳过当前 tick 的订单排序与派单计算；一旦所有候选车匹配完立即 break。在订单大量积压（如 `pub_flood`）场景下加速数百倍。
4. **旋转坐标系热点统计**：$O(NR + (W+H)^2)$ 确定性算法，无论 $R$ 多大均在 0.1ms 内完成，无任何超时风险。
5. **网格占用标记**：`occ_robot[y][x]` 提供 $O(1)$ 的车位互斥检查，杜绝线性扫描。
