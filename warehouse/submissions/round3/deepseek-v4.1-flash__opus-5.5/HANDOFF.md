## 3. 必须保留的基线行为（都是故意的）

- 基线的 BFS 起点可以不可通行（起点记 0，从可通行邻居往外扩），终点必须可通行；
  `DIST(a,b)` 在 `a==b` 时直接是 0。代码里统一由 `distAt()` / `fdist()` 表达这个语义。
- 选车：最近的；一样近取**编号大**的（基线是 `a <= best` 就更新）。
- 选充电桩：先在"没被占、`d + safetyMargin <= 电量`"的桩里取最近的，并列取扫描顺序（先 y 后 x）靠前的；
  一个都没有时退到"最近的可达的桩"（不管占用和电量）。"被占"包含同一 tick 里编号更小的车刚选走的桩。
- 移动：四个邻居按 上、右、下、左 的顺序比较，严格更小才换；被占时连续等待 >= 4 且最优邻居不是目标格才
  `SIDESTEP`，挪到第一个可走且没人的邻居（不要求更近）。
- 死车不占位；救援要求格子上没有别的活车，只充到 `batteryMax / 2`。
- `CANCEL` 只要订单存在就计入 `cancelled`，哪怕随后是 `CANCEL_FAIL`。
- 热点：只跳过墙（被封的格子也参与），严格更大才更新，全是墙时输出 `-1,-1,-1`。

## 4. 优化机制，以及各自为什么不改变输出

### 4.1 距离场缓存（`Slot` / `getField` / `fdist`）
以某个**可通行**格为源的整图 BFS 距离表，按源格缓存。图无向，所以同一张表既当"到目标的距离"
（移动），也当"从这里出发的距离"（派单的 a、b）。地图带一圈墙，BFS 内层无边界判断、无分支。

### 4.2 封路/解封时增量修补（`repairBlock` / `repairUnblock`）
- 封路：标准的"删点后增量最短路"。先按距离从小到大找出"所有父亲都受影响"的格子，再只在这个集合里重算。
  绝大多数事件一个格子都不受影响。受影响集合超过全图 1/4 时放弃修补，作废重算。
- 解封：距离只会变小，从被解封的格子做松弛传播。

### 4.3 有效半径 `validR`
不变量：**场里存的值 <= validR 的可通行格是精确的；存的值更大的，真实距离一定 > validR**
（`validR == INF` 表示整张场精确）。由此得到两个省事的办法：
- 远处的事件不碰场：事件格到源的曼哈顿距离 m+1 是真实距离的下界，事件只可能改变距离 >= m+1 的格子。
  使用者（朝这个目标走的车）当前只需要 `curD` 以内的值，所以 `m >= reach + 2` 时只做 `validR = min(validR, m)`。
- 移动用的场只算到车所在的那一层（`refill(sl, stopCell)`）。

读场的地方（`fdist()`、`moveRobots()`）发现要用的值 > validR 就整场重算，所以 `curD` / `Order::b`
这些估计值**只影响快慢，不影响结果**。直接读 `getField()` 的返回值时必须自己对照 `validR`。

### 4.4 待派队列（`classes` / `PendWalker`）
同一原优先级的订单之间，到达越早有效优先级越不低，所以内部顺序永远是（到达↑, 编号↑），与时间无关。
每个原优先级一个静态有序集合，老化不移动任何订单；派单时对各集合的队首现算有效优先级做多路归并。
`aged` = 到达 tick < `agedPtr` 的待派订单数，`agedPtr` 每 tick 推进到 `t - agingEvery + 1`。

### 4.5 增量派单（`dispatch`）
不变量：每个 tick 派单结束后，"仍待派的订单 × 仍空闲可接单的车"全部试过且失败。车在 IDLE 期间位置、
电量不变；封路只会让距离变大。所以下一个 tick 只需要看 (a) 新空闲的车 × 所有订单，(b) 新进队的订单 × 所有车；
只有**解封**之后才把所有空闲车当作新车重试。按派单顺序扫队列直到新车用完，剩下的新订单再按同样的顺序单独处理。

增量派单内部分两段：先按派单顺序走队列（`PendWalker`），通常队首几张订单就把新车用完；走了 48 张
（`WALK_LIMIT`）新车还没用完，就改成对 `pendFlat`（待派订单的平铺副本）做一趟顺序扫描，只把
"至少有一辆新车满足电量下界"的订单挑出来，和新订单一起按派单顺序处理（`collectCandidates`）。
被筛掉的订单在 `pickRobot` 的第一步用同一个条件就会失败，所以跳过它们不改变结果。

### 4.6 派不出去的订单：三层下界（都只做筛选，筛过了仍走精确计算）
1. `FlatOrder::lower = bLB * carryCost + cLB + safetyMargin`，加上车到取货点的曼哈顿距离。
   `bLB` / `cLB` 是 b、c 的下界：进队时取曼哈顿距离 / 0，算出精确值后换成精确值；封路只会让真实值变大；
   解封格子 z 时取 `min(原值, 经过 z 的路径长度的曼哈顿下界)`（`onMapChange` 里那个循环）。
2. 静态下界（`staticFieldOf`）：只看墙、不看封路的距离永远 <= 真实距离。订单第二次进入"贵路径"时，
   取以它的取货格为源的静态场（按格子缓存，整场运行期间复用）。
3. 都筛不掉才去建/读真正的距离场。

防的是"低电量：空闲车很多但大多数订单接不了"和"很多派不出去的订单 + 地图频繁变化"
（上一轮的两个性能型反例就是后一类）。这类输入下派单仍是最大的开销，是下一步最值得优化的地方。

### 4.7 其他
`goCharge` 对同一（地图版本, 位置）的失败结果做了记忆；事件预解析后按 tick 分桶；日志写进一个字符串最后一次输出；
报表热点按行差分。

## 5. 失效条件 / 改需求时要注意

- **新增会改变地图的事件**：必须走 `onMapChange()`（维护 `pass`、`fieldTmpl`、所有缓存的场、`mapVersion`、`mapChanged`）。
- **让距离可能变小的任何新机制**（不只是解封）都要置 `mapChanged = true`，并像解封那样放宽
  `bLB` / `cLB`，否则 4.5 的不变量和 4.6 的下界都不成立。如果墙本身会变，4.6 的静态场要作废。
- **派单的电量条件如果改了**，`FlatOrder::lower`、`collectCandidates`、`pickRobot` 开头的筛选、静态下界
  这四处要一起改：它们必须都是新条件的必要条件（宁可筛得松，不能筛得紧）。
- **如果 IDLE 的车电量或位置会变**（比如以后加"原地慢充"），4.5 的不变量不成立：要在变化时 `r.isNew = true`。
- **如果有效优先级不再是"原优先级 + 随等待时间单调不减、且对所有订单同一个函数"**，4.4 的静态顺序不成立，
  需要改回按有效优先级排序的结构。
- **订单编号**假设唯一（`check_input.py` 保证）；排序用 `atoi(编号)`。
- 距离用 `uint16_t`，要求 (W+2)*(H+2) < 65534。
- 内存：距离场池上限约 256MB（`slotCap`），静态场池同样上限；实测大负载峰值远小于此。
