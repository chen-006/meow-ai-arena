# 第三轮接手交接文档

## 结果与入口

本轮保留主程的仿真阶段顺序，重写了派单队列、距离缓存及热点统计，并替换输入解析。程序只处理 CHANGE.md 指定的八参数新格式，只使用标准库、标准输入和标准输出。

编译和验收仍使用：

```text
python tools/bench2.py
python tools/bench2.py --big
```

源码职责：

- `main.cpp`：读取、运行、收尾、输出。
- `sim.cpp`：输入解析、事件、救援、充电、寻桩、移动及报表，保持基线阶段顺序。
- `dispatch.cpp`：老化排序、派单、待单统计、永久不可行订单剪枝。
- `util.cpp`：日志、紧凑 BFS、拓扑增量更新、充电距离场及热点统计。
- `common.h`：实体、状态枚举、接口和范围常量。

## 本轮修复与需求变更

1. 修复所有封锁送货点/充电距离反例：基线 BFS 的起点即使被封锁，距离仍为零，仍能向可通行邻居走出。多源充电距离场仅以可通行充电桩为源；查询封锁格时，返回可通行邻居充电距离的最小值加一，而不是直接认为不可达。
2. 修复缓存替换后的旧指针使用：派单只使用一个取货距离场，封锁机器人起点的距离通过邻居查询求得，候选机器人循环不再另起 BFS。借出的缓存指针只在下一次缓存查询前有效。
3. 修复固定 512 槽环形缓存的性能退化：按地图大小分配缓存，使用 16 位距离场和受限地图上的 LRU；小地图能够保留所有源点。
4. 有效优先级使用原始到达时间，重新排队不改变到达时间。送货普通移动及 SIDESTEP 均按移动前状态扣除 carryCost；目标格到达处理先于不足电量停机检查。派单需求为 a + b*carryCost + c + safetyMargin。
5. `REPORT` 在 pending 后输出 aged，待单到达时间计数用 Fenwick 树维护，包括暂不参与派单搜索的订单。

## 老化队列为什么不需要每 tick 全量排序

设 A=agingEvery，tick=kA+r，到达时刻=qA+s，则有效优先级为：

```text
priority - q + k - (s > r)
```

短周期（A <= 1024）按到达余数 s 分桶，各桶维护不可变键 `priority - q`、到达时间、整数订单编号。派单时通过桶首堆合并，省略所有订单共同的 k，得到完全相同的全局顺序。A >= T 时使用单桶，因为本次仿真中不会老化。

更长的周期使用一棵有序集合和按 tick 预约的老化事件。只在订单实际老化时先删除旧键、修改优先级、重新插入。每个订单有代数编号，取消、派出或重新排队使旧预约失效。

集合只维护可参与搜索的待单。静态地图下的最近充电距离是动态地图距离的下界；结合取送货曼哈顿距离，可以证明某些订单即使机器人满电、所有临时封锁都解除也无法派出。静态连通分量不同的取送货点同样永远不可达。这些订单仍保持 PENDING、接受取消并计入 pending、aged、open，只从派单搜索中排除。没有基于经验的近似剪枝。

## 距离缓存与动态封路

距离场按 W*H 一维存储，距离类型为 uint16_t，65535 表示不可达，读取时转换为原始 BIGNUM。合法输入 W,H <= 200，最短简单路径少于 40000 条边，所以该表示不会截断真实距离。地图四周必须为墙；所有 BFS 源点为内部非墙格，这使线性邻居访问不需要重复边界检查。

距离数组总预算为 192 MiB，分配槽数为 min(W*H, 192MiB/(W*H*sizeof(Distance)))。按需分配每槽数组。超过容量时精确 LRU 替换；地图够小时不会替换。订单末段耗电按拓扑版本缓存。

每次有效 BLOCK/UNBLOCK 记录一次拓扑变化，同时更新当前可通行数组。每 64 次变化保存一个封锁位图。距离场过期时：

1. 少量变化直接读取变更历史；历史较长时，用当前位图与旧版本检查点异或，再应用最多 63 次旧版本尾部变化，得到真正发生净变化的格子。
2. 对新增封锁格删除原距离。沿旧最短路径 DAG 传播：只有失去全部前驱的格子才失效。单源起点始终保留距离零，即使被封锁。
3. 从未失效区域的边界，以及新增可通行格，进行队列距离松弛。多源充电场的新增可通行充电桩额外以距离零为源。
4. 当失效/修复工作量超过 `W*H/2+64` 时，立即放弃增量操作并对当前拓扑完整 BFS。此阈值只影响速度，任何返回值都是精确距离。

同一格反复封锁再解封，如果最终状态未变，无需更新距离。临时数组和缓存仅用于当前这一轮仿真，程序一次进程只处理一份输入。

## 其他优化与兼容行为

- 输入一次读入，直接扫描整数与字符串视图；不再为每个事件构造 stringstream。
- 机器人占用查询保持 O(1)。寻桩预约使用稀疏清空的计数数组，避免每个桩再扫描全部机器人。
- 热点用每行区间差分累加曼哈顿菱形，再按 y、x 扫描非墙格；封锁格仍参与候选中心。机器人位置及存活情况未变时复用热点结果。
- 输出日志集中缓冲，最终一次写出。
- 保留所有基线怪行为：等距派单后遍历的机器人获胜；救援等待 100 tick、恢复半电；达到 90% 电量离桩；已知订单的失败取消也计数；平均延迟整数四舍五入；方向顺序上、右、下、左；目标已到达时不检查不足电量。

## 验证记录与性能边界

本轮各主要变更均通过全部 41 个公开、边界和回归用例，三组带标准输出的大负载也逐字节比对通过。另在当前目录 work 下建立独立的“baseline + CHANGE.md”参考程序，做了普通随机、长仿真、密集充电桩、长老化周期对拍；距离缓存还用独立朴素 BFS 直接验证随机拓扑变化后的全部距离。

额外压力负载覆盖 200x160 地图、300 台机器人、12000 tick，20000 tick 长仿真，低电量和每 tick 老化。大地图距离数组预算固定，不会随着订单总数无界增长。复杂封路或狭窄地图可能使增量更新退化，此时完整 BFS 兜底；大量不同源点可能触发 LRU 替换，影响速度但不影响输出。

最终以 tools/bench2.py 的实测为准。Windows CPU 计时有约 15.6ms 粒度，极短负载的加速比会有波动，不能把一次短负载测量当成所有地图的性能保证。

## 终版验收补记

终版重新通过全部 41 个固定用例和三组大负载。一次完整 --big 实测：flood 0.03125 CPU 秒、1088.6 倍；dynamic 0.109375 CPU 秒、618.0 倍；crowded 0.125 CPU 秒、1021.8 倍。短负载的 Windows CPU 计时存在粒度波动。

独立距离测试还覆盖了 200x200 地图的 3500 个不同源点，强制触发 LRU 替换，再检查 100 批拓扑变化，全部与朴素 BFS 一致；-Wall -Wextra 编译无警告。

终版冻结后另完成 400 组新的混合随机对拍，涵盖密集充电桩、封路、短/长老化周期，全部一致；最后一次 bench2.py 仍为 41 个用例全部正确。本轮在 45 分钟内完成，未使用网络或其他模型。
